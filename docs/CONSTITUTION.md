# 프로젝트 헌법 (CONSTITUTION.md)

> 프로젝트: 동잇(Doing_It) — 팀 협업 프로젝트 관리 시스템 | 방식: SDD | 버전: v0.6
> 상위 문서: 팀 협업 관리 시스템 기획서 (정식 문서)
> 하위 문서: [REQUIREMENTS.md](./REQUIREMENTS.md), [SPEC.md](./SPEC.md), [USER-STORIES.md](./USER-STORIES.md), [DATABASE-DESIGN.md](./DATABASE-DESIGN.md), [API-SPEC.md](./API-SPEC.md), [UI-DESIGN.md](./UI-DESIGN.md), [ARCHITECTURE.md](./ARCHITECTURE.md)

이 문서는 기획서가 정한 목표·범위·인원·일정 안에서, 모든 명세, 설계, 코드가 지켜야 하는 **작업 원칙**을 정합니다.

문서 간 우선순위는 **기획서 → 헌법 → 하위 명세(요구사항 명세, 기능 스펙, 사용자 스토리, DB 설계, API 명세, UI 설계, 아키텍처) → 코드** 순서입니다.

- 기획서와 이 문서가 충돌하면 기획서를 따르고, 이 문서를 기획서에 맞게 고칩니다.
- 하위 명세나 AI가 만든 코드가 이 문서와 충돌하면 이 문서가 우선합니다.
- 이 문서를 바꾸려면 팀원 전원의 합의가 필요하고, 바꾼 이유를 맨 아래 변경 기록에 남깁니다.

## 1. 명세 우선

1. 모든 기능은 `REQUIREMENTS.md`에 기능 ID(예: `TASK-01`)와 수용 기준이 있어야 구현을 시작합니다.
2. 명세와 코드가 다르면 **명세를 먼저 고치고** 코드를 맞춥니다. 코드만 바꾸지 않습니다.
3. 작업 순서는 **명세 작성 → AI로 구현 → 개발자 코드 검토 → 테스트 → 명세와 구현 비교**를 반복합니다.

## 2. AI 코딩 도구 사용 규칙

1. AI에게 코드를 요청할 때는 관련 기능 ID, 해당 명세(REQUIREMENTS, API-SPEC, DATABASE-DESIGN의 관련 부분), 이 헌법을 함께 제공합니다.
2. AI가 만든 코드의 정확성과 설계 적합성은 **그 코드를 PR로 올린 팀원이 책임**집니다. 이해하지 못한 코드는 올리지 않습니다.
3. AI가 명세에 없는 기능, 라이브러리, 테이블을 추가하면 그대로 쓰지 않고 지웁니다. 필요하면 명세부터 고칩니다(1-2).
4. 리뷰어는 "AI가 만들었으니 맞을 것"이라고 가정하지 않고, 사람이 쓴 코드와 같은 기준으로 봅니다.

## 3. 팀 운영 (4명 기준)

1. 역할 분담

   | 역할 | 주요 책임 | 담당자 |
   | --- | --- | --- |
   | 백엔드 A | 인증, 프로젝트·멤버 API, 권한 공통 함수, 공통 예외 처리 | 양준석 |
   | 백엔드 B (DB·테스트) | DB 스키마, Alembic 마이그레이션, 업무·변경 이력·대시보드 API, pytest | 서승범 |
   | 프론트엔드 A | 공통 레이아웃·UI 컴포넌트, API 클라이언트, 로그인·회원가입·프로젝트 목록·프로젝트 설정 화면 | 최진영 |
   | 프론트엔드 B | 칸반 보드, 업무 상세, 대시보드·통계 화면 | 김서현 |

   일정 점검, 문서 정리, 시연 준비 등 공통 업무는 4명이 분담합니다.
2. 리뷰는 **다른 영역 담당자도 돌아가며** 맡습니다. 같은 사람끼리만 리뷰하지 않도록 순번을 정합니다.
3. 매일 작업 시작 시 10분 이내로 어제 한 일, 오늘 할 일, 막힌 점을 공유합니다.
4. 결정이 필요한 문제는 30분 이상 혼자 붙잡지 않고 팀에 공유합니다.

## 4. 범위와 우선순위

1. 우선순위는 `REQUIREMENTS.md`의 **P0(MVP) → P1 → P2** 순서를 따릅니다. **P0을 모두 끝내고 테스트가 통과하기 전에는 누구도 P1, P2를 시작하지 않습니다.** 자기 P0을 먼저 끝낸 사람은 다른 사람의 P0을 돕거나 테스트·리뷰를 맡습니다.
2. 다음 기능은 범위에 넣지 않습니다: LLM, RAG, LangChain, AI 에이전트, AI 모델 학습 등 AI 기능(AI는 코딩 도구로만 사용), 실시간 알림(WebSocket), 이메일 발송, 파일 첨부, 외부 서비스 연동, 보기 전용 역할(VIEWER).
3. 새 기능 아이디어는 바로 구현하지 않고 `REQUIREMENTS.md`에 P2로 먼저 추가한 뒤 팀이 판단합니다.

## 5. 기술 스택 고정

| 영역 | 사용 기술 |
| --- | --- |
| 프론트엔드 | React 19, JavaScript, Vite(빌드), React Router(화면 주소), Tailwind CSS 4, Axios, React Hooks + Context API — Node 22 LTS |
| 백엔드 | Python 3.12, FastAPI, Pydantic 2, Uvicorn(ASGI 서버), python-dotenv(.env 읽기) |
| DB / ORM | **MariaDB**, SQLAlchemy 2.x, Alembic, PyMySQL |
| 인증 | JWT(Access Token, PyJWT), bcrypt |
| 테스트 | pytest + httpx(TestClient), Postman |
| 코드 스타일 | 백엔드: ruff(린트) + black(포맷) / 프론트: ESLint + Prettier |
| 협업 | Git, GitHub |

1. 위 목록에 없는 라이브러리를 추가하려면 팀 합의가 필요합니다. 합의한 내용은 README의 의존성 목록에 이유와 함께 적습니다.
2. DB 스키마는 **반드시 Alembic 마이그레이션으로만** 바꿉니다. DB에 직접 DDL을 실행하지 않습니다.
3. 모든 팀원은 같은 MariaDB 버전(10.11 LTS)을 Docker로 실행하고, 같은 Python·Node 버전을 써서 개발 환경 차이를 없앱니다. 패키지 버전은 `requirements.txt`·`package-lock.json`에 고정합니다(`ARCHITECTURE.md` §2).
4. 상태·역할 값은 Python `Enum`으로 정의하고 DB에는 VARCHAR + CHECK 제약으로 저장합니다. (`DATABASE-DESIGN.md` §1·§10)

## 6. 보안과 권한

1. 모든 API는 인증이 기본입니다. 인증 없이 호출할 수 있는 API는 **회원가입과 로그인뿐**입니다.
2. 권한 검사는 **백엔드에서** 합니다. 프론트에서 버튼을 숨기는 것은 사용 편의를 위한 것일 뿐 권한 처리로 보지 않습니다.
3. 권한은 두 단계로 확인합니다.
   - 시스템 역할: `ADMIN`, `USER`
   - 프로젝트 역할: `OWNER`, `MEMBER` (권한 매트릭스는 `REQUIREMENTS.md` 2절)
   - 보기 전용 역할(VIEWER)은 현재 범위에서 제외하고 추후 다시 검토합니다. 나중에 추가하기 쉽도록 권한 검사는 역할 값을 직접 비교하지 않고 공통 함수(예: `require_project_role(...)`)로 모읍니다.
4. 프로젝트 하위 리소스(업무, 댓글, 이력)에 접근할 때는 항상 요청한 사용자가 그 프로젝트의 멤버인지 먼저 확인합니다.
5. 인증은 **Access Token만** 씁니다. 만료 시간은 **2시간**이며, 만료되면 다시 로그인합니다.
6. 토큰은 **localStorage**에 저장합니다. 이에 따라 XSS를 막기 위해 다음을 지킵니다.
   - `dangerouslySetInnerHTML`을 쓰지 않습니다. 사용자 입력은 항상 React의 기본 출력으로 표시합니다.
   - 토큰 값을 콘솔이나 로그에 출력하지 않습니다.
   - 로그아웃하거나 401을 받으면 localStorage의 토큰을 즉시 지웁니다.
7. 비밀번호는 bcrypt 해시로만 저장하고, 응답에 `password_hash`를 절대 포함하지 않습니다.
8. JWT 시크릿, DB 접속 정보 등 비밀 값은 `.env`로 관리하고 Git에 올리지 않습니다. 저장소에는 `.env.example`만 둡니다.

## 7. API 규칙

1. REST 형식을 따릅니다. 자원은 복수형 명사, 동작은 HTTP 메서드로 표현합니다.
   - 예: `GET /projects/{id}/tasks`, `PATCH /tasks/{id}`
2. 응답 형식을 통일합니다.
   - 성공: 리소스 객체 또는 `{ "items": [...], "total": n, "page": 1, "size": 20 }`
   - 실패: `{ "code": "ASSIGNEE_NOT_MEMBER", "message": "담당자는 프로젝트 멤버여야 합니다." }`
3. 상태 코드는 일관되게 씁니다: 400 업무 규칙 위반, 401 인증 실패, 403 권한 없음, 404 없음, 409 중복, 422 입력 검증 실패.
4. 목록 API는 페이지네이션을 지원합니다(기본 20건).
5. API를 바꿀 때는 **`API-SPEC.md`를 먼저 수정**하고, 프론트·백엔드 담당자가 확인한 뒤 코드에 반영합니다.

## 8. 데이터 무결성

1. 업무의 생성, 상태·담당자·마감일·우선순위 변경, 삭제는 반드시 `task_activities`에 이력을 남깁니다. (`LOG-01`)
2. 이력 기록은 업무 변경과 **같은 트랜잭션**에서 처리합니다. 변경이 실패하면 이력도 남지 않아야 합니다.
3. 삭제는 **실제 삭제**를 씁니다.
   - 프로젝트, 업무, 댓글은 실제로 삭제하고 하위 데이터는 CASCADE로 함께 지웁니다.
   - 변경 이력은 업무가 삭제되어도 남깁니다(`task_id`를 NULL 처리).
   - 프로젝트를 지우지 않고 숨기는 보관(`is_archived`) 기능은 P2이며, P0·P1을 모두 마친 뒤 구현한 경우에만 씁니다.
   - 되돌릴 수 없으므로 화면에서는 반드시 확인 단계를 거칩니다.
4. DB 제약(UNIQUE, CHECK, FK)으로 막을 수 있는 규칙은 DB에서 막고, 여러 행에 걸친 규칙(예: OWNER 최소 1명)은 서비스 계층에서 검사합니다.
5. 모든 시각은 UTC로 저장하고 화면에서 한국 시간으로 바꿔 보여줍니다. 문자셋은 `utf8mb4`를 씁니다.

## 9. 테스트와 품질

1. P0 기능의 핵심 API(인증, 권한, 업무 CRUD)는 **pytest 테스트가 통과해야 완료**로 봅니다. 그 밖의 API는 Postman 컬렉션으로 확인하고, 컬렉션 파일을 저장소에 함께 올립니다.
2. 권한 테스트에는 반드시 실패 경우를 넣습니다. (예: 비멤버의 접근은 403, MEMBER가 남의 업무 수정·삭제 시 403, 담당자가 아닌 MEMBER의 상태 변경 시 403)
3. `main` 브랜치에 직접 push하지 않습니다. 기능 브랜치에서 작업하고 **PR 리뷰 1명 이상의 승인**을 받아 병합합니다. GitHub 브랜치 보호 규칙으로 강제합니다.
4. PR을 올리기 전에 포맷터·린터를 실행합니다. **ruff, black, ESLint, Prettier 검사를 통과하지 못한 PR은 병합하지 않습니다.** 자동 검사(CI)는 두지 않으므로, PR을 올린 사람이 로컬 실행 결과(린트, 백엔드는 pytest 포함)를 PR 설명에 한 줄 적고, 리뷰어는 그 줄이 없으면 승인하지 않습니다.
5. 하루 작업이 끝나면 `main`에서 서버와 화면이 실행되는 상태를 유지합니다.

## 10. 이름과 언어 규칙

1. **문서, 커밋 설명, PR 설명, 코드 주석은 한국어**로 씁니다.
2. **변수, 함수, 클래스, 파일, API 경로, DB 테이블·컬럼 이름은 영어**로 씁니다.
   - Python: 변수·함수 `snake_case`, 클래스 `PascalCase`
   - JavaScript: 변수·함수 `camelCase`, 컴포넌트 `PascalCase`
   - DB: 테이블은 복수형 `snake_case` (예: `task_comments`)
3. 커밋 메시지는 `종류(기능 ID): 한국어 설명` 형식입니다. 종류는 `feat`, `fix`, `refactor`, `test`, `docs`, `chore` 중 하나입니다.
   - 예: `feat(TASK-02): 업무 상태 변경 API 추가`
4. 브랜치 이름은 `feat/TASK-02-status-change`, `fix/AUTH-01-login-id-dup`처럼 종류, 기능 ID, 영어 요약을 붙입니다.

## 11. 단순함

1. 지금 필요 없는 추상화나 확장은 만들지 않습니다. 같은 코드가 세 번 반복될 때 공통화합니다.
2. 92시간 안에 끝낼 수 없는 기능은 과감히 빼거나 P2로 내립니다.
3. 칸반 상태 변경은 버튼 방식으로 먼저 완성하고, 드래그 앤 드롭은 P2로 둡니다.
4. 단, 스타터킷으로 재사용할 공통 모듈(인증, API 클라이언트, DB 세션, 예외 처리, 공통 UI 컴포넌트)은 처음부터 분리된 폴더에 둡니다.
