## 3. AI 활용 사례
### 3.1 잘된 예
- **멤버 역할 변경 (PRJ-08, SPEC-CHANGELOG #27 → #113)**
  - 상황: 2순위 기능인데 UI-DESIGN S7에 역할 변경 화면이 없었음.
  - AI에게 준 것: 기능 ID(PRJ-08)와 작업 지시만. "명세에 없는 것은 명세 수정부터 제안한다"는 CLAUDE.md 규칙에 따라 AI가 UI-DESIGN S7에 역할 변경이 없는 것을 찾아 명세 보완안을 먼저 냈고, 승인 뒤 구현함.
  - 결과와 근거: 역할은 드롭다운에서 고르면 바로 적용되고, 나를 MEMBER로 바꿀 때만 확인 창이 뜸. 리뷰에서 동작 수정 없이 병합(#113).
- **API보다 먼저 만든 화면 (PRJ-08 #113, DASH-02 #118)**
  - 상황: 백엔드 API가 아직 없었음.
  - AI에게 준 것: 기능 ID와 "API는 아직 없다"는 상황 설명만. AI가 규칙대로 API-SPEC의 응답 형식을 직접 찾아 그 모양으로 화면을 만듦.
  - 결과와 근거: API가 병합된 뒤 실제 응답으로 바꿔도 화면 코드를 고치지 않음.

### 3.2 AI가 틀렸거나 명세와 달랐던 예
- **README "CORS 때문에 5173으로 열어야 한다" (D11-02)**
  - AI가 만든 것: README 프론트 안내에 위 문장을 씀. 실제로는 화면이 Vite 프록시를 거쳐 `/api`를 부르므로 CORS가 걸리지 않음.
  - 어떻게 발견했나: 서승범의 README PR #167과 충돌이 나서 두 내용을 비교하다가 발견.
  - 고친 방법: 내 README 수정은 빼고 서승범 쪽을 따름. 주석 정리만 #169로 다시 올림. 명세 변경 없음.

## 4. 명세가 AI 결과에 준 영향
- **명세가 자세했던 부분:** SPEC에 따옴표로 적힌 문구와 오류 `code`가 정해져 있어, 화면은 `code`에 맞는 SPEC 문구를 그대로 보여 주었다. 마감 임박·지연은 "오늘"을 서버가 한국 날짜로 계산한다는 명세가 있어, 화면에서 날짜를 다시 계산하지 않고 서버의 `alert` 값과 순서를 그대로 썼다.
- **명세가 비어 있던 부분:** AI가 혼자 정하지 않고 팀장 확인이나 명세 보완을 거쳤다.
  - S3 문구 5개 → 구현하면서 정하고, 팀장 확인 뒤 UI-DESIGN에 올림(SPEC-CHANGELOG #13).
  - 진행 중 업무도 진행률 막대에 따로 보여 주는 안 4가지 → 미리보기로 비교했지만, 명세에 없어 넣지 않음.
  - 업무 0건 멤버 표시 여부 → 처음에는 API 응답대로 표에 나오지 않았으나, 팀장 결정으로 0으로 보이게 바뀜(UI-DESIGN §9 #5, SPEC-CHANGELOG #29).
