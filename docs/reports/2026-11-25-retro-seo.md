## 3. AI 활용 사례
### 3.1 잘된 예 (1~2개)
- **구현·리뷰·계획 중에 명세 빈틈을 찾아 명세부터 고침 (SPEC-CHANGELOG #5·#6·#15·#20)**
  - 상황: 모델·이력·업무 API를 명세대로 만드는데, 명세 문장대로 하면 DB가 잘못된 값을 받거나 구현할 수 없는 곳이 나왔다.
  - AI에게 준 것: DATABASE-DESIGN·API-SPEC 해당 절. "명세와 다르거나 명세에 없는 것이 필요하면 코드보다 먼저 명세 수정을 제안"(CLAUDE.md §7).
  - 결과와 근거: 네 곳 모두 코드보다 명세 수정을 먼저 제안했다.
    - `UPDATED` + `field = NULL`이 CHECK를 통과함(#5) — 구현 중 실제 MariaDB에서 확인
    - `_ci` 콜레이션이라 `'todo'` 같은 소문자도 통과함(#6) — 리뷰 에이전트 지적 후 실패하는 테스트 6개로 확인
    - 설명 길이 규칙이 없어 500이 남(#15, PR #43·#52) — 코드 리뷰 지적 후 7만 자로 재현(MariaDB `Data too long`)
    - 삭제된 업무의 `task_title` 규칙을 구현할 수 없음(#20, PR #69) — 이력 조회 API 계획 중 FK `SET NULL` 구조를 보고 발견
- **보안 점검에서 다른 조 버그 발견 (D10-03, #141 → 이슈 #142)**
  - 상황: DB·입력값 보안 점검으로 경계값 테스트 60개를 만들었다.
  - AI에게 준 것: 목록 API 7개의 page·size 범위, 아주 큰 id, SQL·LIKE 문자열, 대량 할당 필드 목록.
  - 결과와 근거: page가 크면 OFFSET 한도를 넘어 500이 나는 것을 찾았다. A조 코드라 직접 고치지 않고 이슈 #142로 넘겼고, 팀장이 page 상한 1,000,000으로 고쳤다(SPEC-CHANGELOG #34).

### 3.2 AI가 틀렸거나 명세와 달랐던 예 (1~2개)
- **아주 긴 숫자 `assignee_id`로 500 (TASK-07, #97)**
  - AI가 만든 것: 검색 필터 `assignee_id`를 숫자로 받았는데 자릿수 제한이 없었다. 4,300자리가 넘는 값이 Python `int()` 자릿수 한도에 걸려 500이 났다.
  - 어떻게 발견했나: PR 전 리뷰 에이전트.
  - 고친 방법: 실패하는 테스트를 먼저 보고, 패턴을 `none` 또는 1~19자리(BIGINT 범위)로 제한해 422로 바꿨다. 명세 변경은 없다.
- **같은 초 정렬을 실제로는 확인하지 못한 테스트 (LOG-03, #89)**
  - AI가 만든 것: 이력 정렬(`created_at DESC, id DESC`) 테스트가 실행 속도에 기대서, 같은 초가 생기지 않으면 id 정렬을 확인하지 못한 채 통과했다.
  - 어떻게 발견했나: PR 전 리뷰 에이전트.
  - 고친 방법: 이력 시각을 직접 같은 초·역전으로 바꾸는 테스트 2개로 교체했다. 정렬을 망가뜨리면 실패하는 것도 확인했다. 명세 변경은 없다.

## 4. 명세가 AI 결과에 준 영향
- **명세가 자세했던 부분:** 검사 순서, 권한표(담당자는 `status`만, 섞으면 요청 전체 403), 이력 규칙은 AI가 그대로 구현했다. 테스트 이름도 명세 문장을 따라가서(`test_assignee_sends_assignee_id_403_not_400` 등) 마지막 문서 대조(D11-03)에서 근거 테스트를 바로 찾을 수 있었다.
- **명세가 비어 있던 부분에서 AI가 정한 것:**
  - 필터의 잘못된 값(422), 멤버가 아닌 담당자 id(빈 결과), `due_from > due_to`(빈 결과), 빈 PATCH `{}`(200).
  - 코드·테스트로는 정해졌는데 명세에는 마지막 날에야 올렸다(SPEC-CHANGELOG #38, PR #170).
  - 댓글 "수정됨"은 초 단위라 1초 안의 수정은 표시되지 않는다. 설계 한계로 PR에 적고 P2 후보로 넘겼다.

## 5. 다음에 바꿀 것
- **명세에 "예외 입력" 칸을 처음부터 둔다.** 길이 상한, 잘못된 값, 빈 본문, 거꾸로 된 범위를 API마다 적는다. 이번에 나중에 고친 명세 중 #15·#38이 이 칸이었다(#5·#6은 DB 제약, #20은 구현할 수 없는 응답 규칙이라 함께 "제약·예외" 칸으로 묶으면 된다).
- **AI가 정한 동작은 그날 명세에 올린다.** 테스트로 정해 놓고 명세를 마지막 날 대조로 맞추면 그 사이에 프론트·Postman이 문서만 보고 다르게 이해할 수 있다.
- **환경 문제는 처음 겪은 날 SETUP에 적는다.** black 차단·cp949·CRLF는 개발 로그에만 있었고, 같은 문제를 여러 번 다시 풀었다.
