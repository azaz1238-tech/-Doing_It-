## 3. SDD가 효과 있었던 점 (공통)
- **구체적인 명세는 AI가 그대로 옮겼다.** 검사 순서(401→422→404→403→400), 권한표, 이력 규칙, SPEC 따옴표 문구, 마감 임박 기준(오늘~+3일)을 4명 모두 "AI가 그대로 구현했다"고 적음. 마지막 코드 대조(D11-03)에서 문서와 다르게 동작하는 곳 0.
- **"명세 먼저" 규칙(CLAUDE.md §7)이 AI의 행동을 바꿨다.** 명세에 없는 것이 필요하면 AI가 코드보다 명세 수정을 먼저 제안함(서승범 #5·#6·#15·#20, 최진영 #27). 동결 후 변경 37건이 모두 SPEC-CHANGELOG에 남음.
- **명세를 계약으로 써서 기다리지 않았다.** 화면은 API-SPEC 응답 모양이나 목 데이터로 먼저 만들고, API가 병합된 뒤 코드를 고치지 않고 연결함(최진영 #113·#118, 김서현 #14·#15).
- **만든 조가 아닌 조가 명세로 검증했다.** 수용 테스트 75개를 상대 조가 화면·API·DB로 확인했고, 보안 점검에서 다른 조 버그(page 500, #142)를 찾음.

## 4. AI 활용에서 배운 것 (공통)
- **AI가 잘한 것:** 명세 절을 주면 스키마·서비스·화면·테스트를 한 번에 만듦. 명세 빈틈을 찾아 수정안을 냄. 검증 결과서·PR 설명·문서 초안.
- **AI가 자주 놓친 것:** 정상 입력이 아닌 경우. 4명이 적은 사례가 모두 경계·예외 쪽이었음.
  - 극단값: 아주 긴 숫자 `assignee_id` → 500(#97), 아주 큰 page → 500(#142), 7만 자 설명 → 500(#15)
  - 검사 순서: 본문 아이디 조회를 권한 검사보다 먼저 함 → 가입된 아이디 노출(#14)
  - 확인 범위: 같은 초 정렬을 확인하지 못한 테스트(#89), 값을 한 번에 넣는 화면 스크립트(#86), 1280px에서만 잰 간트(#149)
  - 문서: 그럴듯하지만 틀린 README CORS 설명(D11-02), 테스트를 실제보다 넓게 인용(#138)
- **잡아낸 방법:** AI 혼자 확인한 것보다 **다른 눈**이 더 많이 잡음 — PR 전 리뷰 에이전트(서승범), 팀원 코드 리뷰(#14·#86), 상대 조 검증·화면 확인(#149), 문서끼리 대조(CORS).

## 6. 발표·최종 보고서에 쓸 내용
1. **명세가 구체적인 곳은 AI가 그대로 옮겼다** — 마지막 코드 대조에서 문서와 다른 동작 0, 동결 후 명세 변경 37건 전부 기록.
2. **AI가 놓친 것은 모두 "예외"였고, 잡은 것은 사람의 리뷰와 교차 검증이었다** — 극단값 500 3건, 검사 순서 1건, 좁은 확인 범위 3건.
3. **다음에는 명세에 "예외·실패·문구" 칸을 먼저 채우고, AI가 정한 동작은 그날 명세에 올린다.**
