## 3. AI 활용 사례
### 3.1 잘된 예
**① 로그인 계정 존재 숨기기 (AUTH-02, SPEC-CHANGELOG #8)**
- 상황: 로그인 아이디 형식 오류를 회원가입처럼 422로 내면 "없는 아이디"와 구분돼 계정 존재가 드러남
- AI에게 준 것: API-SPEC §5.1 + "로그인 실패를 구분할 수 없게"
- 결과: 형식 오류·없는 아이디·틀린 비밀번호를 모두 401 `INVALID_CREDENTIALS`로, 비활성 403은 비밀번호가 맞을 때만 알려 줌. 명세를 먼저 고친 뒤 구현

**② 동시성 버그를 테스트로 찾기 (PRJ-05·PRJ-08)**
- 상황: 마지막 OWNER 규칙은 여러 행에 걸친 규칙이라 동시에 두 요청이 오면 깨질 수 있음
- AI에게 준 것: DATABASE-DESIGN §6.1 잠금 순서 + "동시 요청 테스트"
- 결과: `SELECT … FOR UPDATE` 잠금 구현. 동시성 테스트로 역할 변경 응답 500(커밋 뒤 삭제된 행을 다시 읽음)을 찾아, 응답을 커밋 전에 만들도록 고침. 수정을 되돌리면 3번 모두 실패하는 것까지 확인

### 3.2 AI가 틀렸거나 명세와 달랐던 예
**① 멤버 추가의 검사 순서 (PRJ-04, SPEC-CHANGELOG #14)**
- AI가 만든 것: §1.5 "404 → 403"을 글자 그대로 따라 본문 `login_id` 조회(404)를 권한 검사(403)보다 먼저 함
- 발견: 코드 리뷰(T-F3-01) — 비멤버도 이 API로 가입된 아이디를 알아낼 수 있음
- 고친 방법: "본문 조회는 권한 검사 뒤"를 명세에 적고 코드 수정. 멤버 제거(#16)에도 같은 규칙 적용

**② `core/` 스타터킷 규칙 위반 (SPEC-CHANGELOG #4)**
- AI가 만든 것: `get_current_user`를 `core/auth.py`에 두고 `app/models`의 `User`를 import
- 발견: T-F0-08 작업 중 — "`core/`는 `app/`를 import하지 않는다"(성공 기준 8)와 충돌
- 고친 방법: `core/`에는 토큰 검사만 남기고 사용자 조회는 `app/services/auth_service.py`로 옮김. 11/25 확인 결과 `core/` → `app/` import 0건

## 4. 명세가 AI 결과에 준 영향
- 명세가 자세했던 부분(오류 코드·검사 순서·트랜잭션 범위)은 AI 결과를 거의 그대로 쓸 수 있었고, 리뷰도 "명세와 같은가"만 보면 됐음
- 명세가 비어 있던 부분에서 AI가 마음대로 정한 것: 로그인 입력 검증(#8), 비활성 계정을 멤버로 추가하는 경우(#14 ②), 설명 길이 상한(#15 — 없어서 7만 자가 500), `page` 상한(#34 — 없어서 아주 큰 값이 500). 빈칸은 대부분 "경계값·실패 경우"였음

## 5. 다음에 바꿀 것
1. **코드보다 명세를 먼저 고치는 규칙을 지킴.** 코드가 먼저 들어가 명세를 뒤늦게 맞춘 것이 4건(#21·#22·#23·#30)이고 4건 모두 내가 바꾼 것이었음. AI가 빨리 만들어 주다 보니 순서를 건너뛰기 쉬웠음
2. **명세에 경계값·상한을 처음부터 적음.** 길이·페이지·동시 요청처럼 AI가 비워 두는 부분을 명세 체크리스트로
3. **테스트 기준을 하나로.** pytest 팩토리와 Postman 컬렉션이 같은 명세 변경을 따라가게(#21 회귀 51개)
